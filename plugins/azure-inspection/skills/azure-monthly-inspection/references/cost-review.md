# 月度成本巡检（01）与虚拟机规格优化（02）

每月帮客户回答：**钱花在哪里、为什么变化、哪些地方可以省、应该先做什么，以及已做的调整实际省了多少。**参考 Azure Well-Architected Framework 的成本优化建议；以降低成本为重点，同时保留业务要求的性能、可用性、数据保留和恢复能力。

## 范围与数据

- **覆盖范围**：覆盖全部纳入范围的订阅，按业务线、订阅、资源组、服务和区域分析费用，区分生产、测试、开发和灾备。
- **订阅清单核对**：每月核对订阅的新增、停用和访问权限。无法读取的订阅或资源单独列出，**不把缺数据当成没有费用或资源闲置**。
- **统计期间**：以上一个完整自然月为主，与前一个月比较，结合历史趋势和业务周期。
- **数据来源**：
  - Azure Cost Management：实际费用、分摊费用、预算、预测。
  - 资源配置和 Azure Monitor：资源规格、运行状态、CPU、内存、磁盘。
  - RI/SP 记录：现有预留和节省计划的使用率（近 7 天、30 天）和到期时间。需要“预留读取者”（Reservations Reader）或计费账户读取权限；没有时如实写“未能核对”，并列为需要客户提供。按资源的计价方式和 Azure 购买建议只需成本读取权限。
  - 客户业务信息：资源负责人、重要任务、增长计划、必须保留的容量。
- **两种费用口径**：实际费用用于看账单支出；分摊费用把 RI/SP 预付费用分摊到使用期间，便于比较各月和各业务。报告中两者分开写。

## 每月检查内容

| 检查内容 | 看什么 | 给客户的结果 |
|---|---|---|
| 费用变化与预算 | 上月总费用、与前月相比的变化、主要服务和资源占比、预算偏差、下月预测；拆解变化原因（新增资源、用量增长、单价或优惠变化） | 费用总览、主要增长原因、异常和预算风险 |
| 资源利用率与规格 | 虚拟机和 AKS 节点的 CPU、内存、磁盘余量；数据库、缓存的容量与实际用量；开发测试是否需要全天运行 | 保持原配置或调整规格的建议、调整前后价格、预计节省、需要确认的事项 |
| 闲置与遗留资源 | 未挂载磁盘、未关联公网 IP、长期快照、已断开的私有终结点、已释放虚拟机仍在收费的附属资源（M3 起加入孤立资源查询库） | 待确认用途的资源清单和处理建议 |
| RI/SP 与采购选择 | 分摊费用中 RI/SP 覆盖的比例；现有预留和节省计划近 30 天使用率（低于 80% 为未用满）、90 天内到期；Azure 基于过去 30 天用量的购买建议；结合降配和迁移计划比较按需与 1 年/3 年 RI、SP | 01 的“RI与SP”“Azure购买建议”两页和“RI 与 SP”一节；先降配稳定后再按新用量采购，避免闲置承诺 |
| 存储、备份与日志 | 容量增长、访问频率与层级、备份和快照保留、日志摄取量和保留、调整层级的读取和提前删除费用 | 可调整的层级、保留和采集配置，预计节省和限制 |
| 架构成本评审 | 重点业务的资源数量、服务档位、扩缩容方式、数据流和网络费用 | 需要深入评估的调整方案、费用比较、影响和优先级 |

先从费用高、增长快或有明确浪费迹象的服务入手。

## 虚拟机规格判断规则（02）

- **CPU 和内存分别判断**：准备减少的那一项，平均利用率低于 20%；另一项容量保留。每次最多减半，同代规格保留所需功能（临时盘、加速网络、安全配置等）。
- **磁盘余量**：目标虚拟机的 Cached/Uncached IOPS 和吞吐平均消耗率各不超过 50%，分别计算、不相加。
- **数据要求**：要有 7 天有效数据、采样覆盖足够；指标按每日平均用采样数加权。缺指标、缺报价、缺规格信息时，不建议调整，并写明原因。
- **部署条件**：检查目标规格在该订阅、区域、可用区是否可部署；磁盘数、网卡数、架构是否满足；价格要更低。
- **节点池**：VMSS 和 AKS 节点池按池统一评估，池内所有运行中的节点有共同目标才调整。
- **价格**：用 Azure 官网公开列表价，包括按需、1 年/3 年 RI、1 年/3 年 SP。Windows 按需价含许可费。已停机的机器不建议购买 RI/SP。
- **已被 RI/SP 覆盖的机器**：巡检月份一半以上分摊费用由 RI/SP 覆盖的机器，降配不会直接减少预付费用（预留额度会转去覆盖其他机器或闲置）。02 在逐台说明里注明“需先交换预留或调整覆盖范围”，正文写明这部分预计节省的金额；读不到按资源的计价方式时，提示实际节省可能低于预计。
- **规则的性质**：这些数值是容量筛选规则，不是 Microsoft 对所有业务规定的安全线。正式调整前仍需确认重要任务、短时高负载和故障接管需求。
- **交叉核对**：出包前必须做 `cross-checks.md` 的 X1–X3：峰值、磁盘吞吐上限、节点池内存压力。

## 架构评审如何开展

围绕具体费用问题展开，不做没有业务目标的全面改造：

- **计算费用高**：比较规格、节点数量、扩缩容方式，检查非生产环境运行时间。
- **数据库或缓存费用高**：检查容量、服务档位和实际访问需求，看是否有重复实例。
- **存储和日志增长快**：检查层级、保留时间、重复数据和采集范围。
- **网络费用增长**：定位出站、跨区域传输和收费网络组件。

每项方案比较预计减少的持续费用、一次性调整费用、业务影响和实施条件；需要迁移或改应用的，先形成评估建议，由客户决定是否立项。

## 费用与节省怎么写

- **历史费用**：用客户 Cost Management 数据，注明统计期间、币种、实际或分摊费用；未结算数据标注查询日期。
- **公开报价**：一律写明“Azure 官网公开列表价”，不是客户合同价或实际账单价。
- **预计节省**：比较同一批资源、相同用量、相同期间的调整前后费用；规格和优惠同时调整时，直接比较最终方案费用。
- **实际节省**：结合调整后的费用、用量和业务变化确认，区分“用得少了”和“单价降低了”。
- **只计算有依据的项目**：未确认用途、不能部署、数据不足或尚待批准的建议，不算作已完成的节省；无法量化的写明原因，不给出没有依据的金额。

## 月度评审

每月交付成本报告、资源与优化建议明细、建议执行与效果跟踪表，并与客户一起确认：

- 费用增长和异常是否有业务原因。
- 哪些建议可以执行，哪些要补数据，哪些因业务要求保留。
- 优先级、负责人、完成时间。
- 已完成的调整是否影响业务，实际节省是否符合预期。

巡检本身不触发任何变更。降配、停机、删除、修改保留策略、购买 RI/SP，都需客户明确批准；生产调整先小范围试用。
