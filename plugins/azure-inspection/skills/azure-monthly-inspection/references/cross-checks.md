# 跨报告交叉核对

六份报告由不同的检查得出，可能互相矛盾：成本报告建议降配，性能报告却说同一资源负载过高。客户同时读到两份，会得到相反的建议。打包前必须逐条核对下列规则。由 `crosscheck` 命令自动核对，结果写入 `findings/crosscheck.json`，每条冲突附建议做法；处理后（写进说明文件并重新 build）再跑一次，会显示“已处理”。

## 规则

| 编号 | 核对什么 | 冲突时怎么处理 |
|---|---|---|
| X1 | **降配建议 vs 性能峰值**：02 建议降配的虚拟机，在 04 中是否有 CPU、内存或 IO 很多天打满 | 在 02 中加提醒，或改为“不更换”（由用户决定），并在表后说明 |
| X2 | **降配建议 vs 磁盘吞吐上限**：降配后新规格的虚拟机磁盘吞吐上限，是否低于已挂数据盘的上限，而 04 显示数据盘带宽经常打满 | 查官方规格表核对两个上限；新规格上限更低的加提醒 |
| X3 | **节点池降配 vs 内存压力**：02 建议降配的 AKS 节点池，在 04 中内存是否长期接近或超出可分配量 | 加提醒：先解决内存问题，不宜只降 CPU |
| X4 | **缓存或数据库降档 vs 增长趋势**：01 列为低利用率、可降档的实例，在 04 中是否快速增长 | 从降档候选中去掉，并注明原因 |
| X5 | **闲置资源 vs 仍在使用**：01 列为闲置的资源，在 03/04 中是否有流量、告警、依赖，或（网卡、公网 IP）在网络安全检查中被列为问题 | 改为“需要确认用途”；确是残留的，03 的建议改为直接清理 |
| X6 | **数字一致**：00 汇总报告里的问题数、费用、节省，与 01–05 是否一致 | 以明细报告为准修改汇总 |
| X7 | **订阅数一致**：各报告的订阅范围和数量 | 统一写法，包括已停用、已删除订阅的说明 |
| X8 | **同一资源的严重程度和建议一致**：同一资源在 03、04、05 中的建议是否一致，例如是“原地开启高可用”还是“按标准模块重建” | 以同类对比得出的根本原因为准，统一修改 |
| X9 | **图表与表格一致**：图表数字与表格是否一致；更新数据后图表是否重新生成 | 重新生成图表 |
| X10 | **汇总结论数字与表格一致**：00 结论段落里的金额和百分比，是否都出现在 00 第 1 节表格中 | 以表格为准改写 `narrative/00.json` 的 `conclusion`；引用明细报告里其他数字的，核对无误即可 |
| X11 | **预测覆盖不全时如实说明**：下个月的预测没有读到的订阅占本月费用 5% 以上时，说明文件里写的预测（01 的 `forecastSummary`、00 的 `conclusion` 里提到下个月预计的句子）是否写了“预测不完整” | 改写这些说法：写明预测不完整，或去掉全部订阅预计的说法，重新生成 |
| X12 | **AKS 升级目标不低于标准支持版本**：05 的 AKS 标准版本和偏差建议、联动到 03/04 问题清单“对齐标准的做法”的建议（`findings/peer/links.json`），以及说明文件（05、03/04 的 `topIssues` 和 `findingTextOverrides`、00 的 `immediate`）里写的升级目标版本，是否低于集群所在区域最低的标准支持版本（03 的 R9/S-I3 用同一份版本表判断“已超出标准支持”） | 05 结果和联动建议：用 0.10.7 或更新版本重新 analyze 再 build；说明文件：改写版本号，至少为最低的标准支持版本 |

## 核对方法

- **X1–X3**：以 02 的“建议调整”清单为准，逐台查 04 的性能问题和原始指标。X1/X2 每条写明冲突类型（CPU、内存、IO）和级别：**直接冲突**是 02 要减少的正是 04 报满的资源（如 04 内存高而 02 要减内存），建议改为不更换或写明理由；**方向不同**是 02 不减这一项（如只减 CPU）而 04 建议增加，写一句说明即可。04 的 P1/P4 会自动注明 02 对同一台机器的建议。磁盘吞吐上限用 Resource Graph 读取磁盘的 `diskMBpsReadWrite` 或层级，虚拟机上限查 Microsoft Learn 的规格页。
- **X4**：以 01 的降档候选为准，查 04 的 P5 结果和最近 30 天趋势。
- **X6–X7**：脚本统计各报告中的数字，与问题清单和费用数据比对。X6 只看正确的数字是否出现在 00 中；00 的表格由脚本生成，总会有这些数字，所以结论里写错的数字要靠 X10。
- **X10**：取 00 结论段落里的 USD 金额（带不带小数都查）和带小数的百分比（“约 44%”“约 USD 1.2 万”这类约数不查），表格中没有的逐条列出，并注明 01–05 哪份报告里有这个数字。结论可以引用明细报告里的其他数字，所以是“需人工确认”，不影响打包。按完整数字比较（2.5% 不算出现在 12.5% 里）；结论里的数字是表格数字四舍五入来的（如 14.8% 对 14.82%，USD 8,315,402 对 USD 8,315,402.37），算一致。
- **X11**：脚本生成的 01 预测句和 00 关键数字在预测不全时会自动写“预测不完整”，并且只和有预测的订阅自己的本月费用比较，所以 X11 只看说明文件里 agent 自己写的预测说法。没写“预测不完整”时为“需要处理”，不能打包。
- **X12**：只看“升级到 1.xx”这类升级目标和 05 的标准版本，不看集群的当前版本。低于最低的标准支持版本时为“需要处理”，不能打包。
- 每处冲突修改后，重新生成受影响的报告和图表，再跑一遍质量检查。
- **只做了部分报告时**（`customer.yaml` 的 `report.include`）：规则需要的报告本月没选时显示“不适用”并写明缺哪份（X1–X3 要 02 和 04 的性能效率，X4 要 01 和 04 的性能效率，X5 要 01 以及 03 或 04，X8 要 03 或 04，X11 要 01，X12 要 03 的可靠性；03/04 只做部分支柱时，X5、X8 只看所做支柱的问题），不影响打包；X6、X7、X9、X10 只核对所选报告。“未检查”则是选了但数据缺失，要查明原因。

## 交付时说明

向用户汇报时，列出发现的冲突、处理方式和依据。只加了提醒而没有改建议的（例如保留降配建议），要明确告诉用户，由用户决定是否更保守。
