# 跨报告交叉核对

六份报告由不同的检查得出，可能互相矛盾：成本报告建议降配，性能报告却说同一资源负载过高。客户同时读到两份，会得到相反的建议。打包前必须逐条核对下列规则。由 `crosscheck` 命令自动核对，结果写入 `findings/crosscheck.json`，每条冲突附建议做法；处理后（写进说明文件并重新 build）再跑一次，会显示“已处理”。

## 规则

| 编号 | 核对什么 | 冲突时怎么处理 |
|---|---|---|
| X1 | **降配建议 vs 性能峰值**：02 建议降配的虚拟机，在 04 中是否有 CPU、内存或 IO 很多天打满 | 在 02 中加提醒，或改为“不更换”（由用户决定），并在表后说明 |
| X2 | **降配建议 vs 磁盘吞吐上限**：降配后新规格的虚拟机磁盘吞吐上限，是否低于已挂数据盘的上限，而 04 显示数据盘带宽经常打满 | 查官方规格表核对两个上限；新规格上限更低的加提醒 |
| X3 | **节点池降配 vs 内存压力**：02 建议降配的 AKS 节点池，在 04 中内存是否长期接近或超出可分配量 | 加提醒：先解决内存问题，不宜只降 CPU |
| X4 | **缓存或数据库降档 vs 增长趋势**：01 列为低利用率、可降档的实例，在 04 中是否快速增长 | 从降档候选中去掉，并注明原因 |
| X5 | **闲置资源 vs 仍在使用**：01 列为闲置的资源，在 03/04 中是否有流量、告警或依赖 | 改为“需要确认用途” |
| X6 | **数字一致**：00 汇总报告里的问题数、费用、节省，与 01–05 是否一致 | 以明细报告为准修改汇总 |
| X7 | **订阅数一致**：各报告的订阅范围和数量 | 统一写法，包括已停用、已删除订阅的说明 |
| X8 | **同一资源的严重程度和建议一致**：同一资源在 03、04、05 中的建议是否一致，例如是“原地开启高可用”还是“按标准模块重建” | 以同类对比得出的根本原因为准，统一修改 |
| X9 | **图表与表格一致**：图表数字与表格是否一致；更新数据后图表是否重新生成 | 重新生成图表 |

## 核对方法

- **X1–X3**：以 02 的“建议调整”清单为准，逐台查 04 的性能问题和原始指标。磁盘吞吐上限用 Resource Graph 读取磁盘的 `diskMBpsReadWrite` 或层级，虚拟机上限查 Microsoft Learn 的规格页。
- **X4**：以 01 的降档候选为准，查 04 的 P5 结果和最近 30 天趋势。
- **X6–X7**：脚本统计各报告中的数字，与问题清单和费用数据比对。
- 每处冲突修改后，重新生成受影响的报告和图表，再跑一遍质量检查。

## 交付时说明

向用户汇报时，列出发现的冲突、处理方式和依据。只加了提醒而没有改建议的（例如保留降配建议），要明确告诉用户，由用户决定是否更保守。
