# Azure 月度巡检（只读）

用客户提供的只读账号读取 Azure 配置、指标和费用，生成给客户的中文巡检报告。每月一次，可与上月对比。

| 编号 | 报告 | 内容 |
|---|---|---|
| 00 | 汇总报告 | 总体结论、需要立即处理的问题、处理计划 |
| 01 | 月度成本巡检 | 费用、变化原因、闲置资源、存储和日志、建议与跟踪 |
| 02 | 虚拟机利用率与规格优化 | 建议汇总、调整前后价格、预计节省；逐台明细在 Excel |
| 03 | 可靠性与安全巡检 | 问题清单（Excel）和报告 |
| 04 | 卓越运营与性能效率巡检 | 问题清单（Excel）和报告 |
| 05 | 同类资源配置对比 | 找根本原因，给出对齐客户标准做法的建议 |

## 当前版本能做什么

版本 0.10.10 可以：

- 准备：环境检查、建客户工作目录、核对只读访问
- 生成全部 6 份报告：**00 汇总**、**01 月度成本**、**02 虚拟机规格**、**03 可靠性与安全**、**04 卓越运营与性能效率**、**05 同类资源配置对比**（采集、分析、生成、核对）
- 按客户选择只做一部分：01–05 在 `customer.yaml` 的 `report.include` 中选择，03/04 还可以只做其中的支柱（可靠性、安全、卓越运营、性能效率）；00 只汇总所选内容；采集只补所选内容要用的数据
- 只查客户指定的订阅（`scope.includeSubscriptions`）：报告写明所选订阅，跨月跟踪不把没检查的订阅算作已解决
- 跨报告交叉核对（X1–X12）和打包
- RI/SP：分摊费用中的覆盖比例、现有预留和节省计划的使用率与到期、Azure 购买建议；02 标出已被 RI/SP 覆盖、降配节省不能直接实现的机器
- 跨月跟踪：03/04 自动与上月比，分出新增问题、新增检查项发现、仍未处理、已解决、本月未检查
- 大租户：费用采集中断后用 `--resume` 续采；资源组很多的订阅按批读取逐资源费用；逐资源明细单独存放，成本模型文件更小，00 生成更快
- 网络设备（防火墙、流量探针等）：按镜像和系统识别，不当作普通虚拟机检查（不判断内存读数、不报 IP 转发、不给降配建议，SSH 建议改为管理口访问控制）
- 检查 Markdown 报告

- 并入微软公开规则库：APRL（可靠性）、Defender/Policy（安全）、孤立资源（01）、AMBA 告警基线（04）、Landing Zone 清单（03 架构对照）（见文末“开发进度”）。**还没有提供的命令，不要自己写脚本去访问客户环境代替**；告诉用户这部分尚未提供。

## 必须遵守的规则

完整规则见 `references/safety.md`，下面是要点：

1. **只读**：
   - 只通过本 skill 的脚本访问 Azure。脚本只允许读取，会拦截写操作和取密钥的操作。
   - 不用 kubectl，不取 AKS 凭据，不扫描端口。
2. **不动用户的登录状态**：
   - 永远不执行 `az login`、`az logout`、`az account set`。
   - 需要登录只读账号时，请用户自己执行。
   - 脚本会核对令牌属于 `customer.yaml` 里的只读账号和租户，不一致就停止。
3. **读不到就如实记录**：遇到 401/403/404 记录后继续，不绕过权限。缺数据不当 0：读不到的费用不是 0 元，读不到的指标不是“利用率低”。
4. **客户数据只放在客户工作目录**，不放进 skill 目录，不上传。报告中不出现邮箱。
5. **降配、删除、购买 RI/SP 等建议需要客户确认后执行**：在建议处理顺序或范围说明里统一写一次，不要每一行都重复。
6. **只通过说明文件改报告**：不要直接编辑 `reports/` 或 `package/` 里的文件。重新生成会覆盖手改的内容，也绕过了核对。
   - 要改文字，就改 `narrative/*.json` 后重新 build。
   - 发现脚本自动生成的文字有错、说明文件改不了时，告诉用户这是插件问题，不要手改报告。
7. **只运行本 skill 规定的命令**：
   - 命令被拒绝或运行环境不允许时，停下来告诉用户，不要自己写脚本包装或代替 skill 的命令。
   - 不要设置 `AZINSPECT_NO_EXCEL`，它只供单元测试使用。Excel 复算失败或跳过时，如实告诉用户，并在交付说明里写明。
   - 不要结束不是自己启动的进程（例如卡住的 Excel），停下来告诉用户。

## 运行脚本

下文 `<skill>` 指本 SKILL.md 所在的目录。在 Claude Code 中它显示为本 skill 的 Base directory；在其他 agent 中，用 SKILL.md 的路径去掉文件名得到。所有命令都这样运行：

```bash
python "<skill>/scripts/azinspect_cli.py" <命令> [参数]
```

命令输出是中文，直接转述给用户即可。

## 第一步：准备（每个新客户做一次）

1. **检查环境**：

   ```bash
   python "<skill>/scripts/azinspect_cli.py" doctor
   ```

   缺依赖时，告诉用户输出里的安装命令，经同意后再执行。缺中文字体会导致图表乱码。

2. **建客户工作目录**：问用户目录放在哪里。工作目录在 skill 目录之外，每个客户一个，例如 `~/inspections/<客户>`。

   ```bash
   python "<skill>/scripts/azinspect_cli.py" init --workspace "<工作目录>"
   ```

3. **填写 `customer.yaml`**：向用户要以下信息，其余字段按模板注释和用户说明填写：
   - 客户名称
   - 文件名前缀
   - 租户 ID
   - 只读账号的 UPN（或服务主体 appId）
   - 一个只读账号能访问的订阅 ID（用来取令牌）
   - 订阅范围（`scope.includeSubscriptions` / `excludeSubscriptions`；客户只想查关键订阅时只列这些）
   - 环境命名规则
   - 业务线规则
   - 要做哪几份报告（`report.include`，默认 01–05 全做；00 总是生成，只汇总所选报告）

   不要猜租户和账号。

4. **请用户用只读账号登录 Azure CLI**（用户自己执行 `az login`）。之后核对访问：

   ```bash
   python "<skill>/scripts/azinspect_cli.py" access-check --workspace "<工作目录>"
   ```

   向用户说明以下几项，并请用户确认范围：
   - 能看到多少订阅：纳入、已停用、被排除各多少
   - 资源能否读取
   - 费用能否读取
   - 账号有没有可写角色（如所有者、参与者）。有的话明确提醒用户：脚本只发读请求，但建议客户改给只读角色；由 AI agent 执行时风险更高

   只读账号建议的权限（都只读）：

   | 权限 | 范围 | 用于 |
   |---|---|---|
   | 读者（Reader） | 各订阅或根管理组 | 配置、指标、活动日志 |
   | 成本管理读者（Cost Management Reader） | 各订阅 | 01 费用、按资源的 RI/SP 覆盖、Azure 购买建议 |
   | Log Analytics 读者 | 日志工作区 | 日志摄取来源、AKS 调度事件 |
   | 安全读者（Security Reader） | 各订阅 | Defender 建议 |
   | 预留读取者（Reservations Reader） | 租户 | 现有 RI/SP 的使用率和到期（可选） |
   | Microsoft Graph 目录读取 | 租户 | 高权限账号、来宾、凭据到期（可选） |

   缺少可选权限时，对应检查如实写“未能核对”，不影响其他报告。

## 第二步：月度巡检

`--month` 是巡检的月份（已结束的完整月），例如 10 月上旬巡检 9 月就写 `2026-09`；不写时默认上一个完整月。`--part` 可选 `cost`（01）、`vm`（02）、`waf`（03、04）、`peer`（05）、`summary`（00，只用于 build）或 `all`。

各步只做 `customer.yaml` 的 `report.include` 中选中的报告，`--part all` 也一样；没选的部分会提示跳过。只选一部分时，采集会自动补上所选报告要用的数据，不用另外操作：只选 01 时采虚拟机清单（不读 30 天指标）；只选 02 时只读 RI/SP 覆盖；选了 04 或 05 时采它们要读的支柱原始数据（不生成 03）。选了 03 但没选卓越运营时，只读运营支柱的资源清单（03 的架构总览要用），不当作卓越运营分析。选了 04、没选 01 时，04 中依赖费用数据的几项（日志用量、预算、按费用挑选存储账户）缩小范围，报告里会写明。交叉核对中涉及没选报告的规则显示“不适用”；打包只包含 00 和所选报告。

用户要求只做部分报告或部分订阅时：

- **先用编号复述并确认**，再改 `report.include`。用户说的是名称或排除（如“不要包含成本”“只做安全”）时尤其要确认，例如“将做 03、04、05，不做 01 月度成本、02 虚拟机规格，对吗？”。“成本”默认指 01 和 02。03、04 可以只做其中的支柱：`report.include` 写支柱名（`可靠性`、`安全`、`卓越运营`、`性能效率`），例如“只做可靠性”写 `['可靠性']`；写 `03` 等于可靠性和安全都做。只做部分支柱时，报告编号不变，标题和文件名只写所做的支柱（如 `03_可靠性巡检报告`）。用户的说法按下表对应，对应不上或跨几类的要问清楚，复述时写出支柱名和报告编号（例如“只巡检高可用”复述为“只做 03 的可靠性部分”）：

  | 用户常说 | 对应 |
  |---|---|
  | 高可用、容灾、备份、可用区、故障恢复、版本到期 | 可靠性（03） |
  | 安全、权限、账号、公网暴露、端口、密钥、加密、Defender | 安全（03） |
  | 监控、告警、日志、运维、治理、标签、预算告警 | 卓越运营（04） |
  | 性能、容量、资源使用率、扩缩容、瓶颈 | 性能效率（04） |
  | 成本 | 01 和 02（默认，见上） |
  | 费用、账单、闲置资源 | 01 月度成本 |
  | 降配、虚拟机规格、RI、SP、预留 | 02 虚拟机规格 |
  | 标准做法、配置不一致、同类对比 | 05 同类资源配置对比 |

- **只做部分订阅**：改 `scope.includeSubscriptions`（名称、`*` 通配或订阅 ID）或 `excludeSubscriptions`。先列出将检查的订阅名称请用户确认（可用 access-check 的输出核对名称）。告诉用户：Entra ID 账号与凭据、管理组（Landing Zone 对照）、预留和节省计划订单不按订阅划分，仍按全租户检查；报告会写明“按贵司选择，本次只检查 N 个订阅”；依赖其他订阅资源的检查（如专线网关连接的专线线路）会写明可能漏报，不算作已解决；维护配置、备份、活动日志告警建在其他订阅时可能多报，也会写明。
- **说明这是长期设置**：改后每个月都按它执行。用户说“这个月”“这次”时，做完（打包后）改回原来的值，并告诉用户已改回。已生成月份的报告选择记在 `findings/selection.json`，改回不影响它。
- **说明文件要跟着选择改**：脚本不会过滤 `narrative/` 里没选的报告或支柱的内容。只做一部分时，先按本次选择改写 00、03、04 的说明文件；同一个月改回全部再生成时，也要按全部改写。换了选择而说明文件没有改过时，build 会停下并列出这些文件；确认内容仍然适用才加 `--narrative-checked`。

1. **采集**（只读，访问客户环境，约 10–30 分钟）：

   ```bash
   python "<skill>/scripts/azinspect_cli.py" collect --workspace "<工作目录>" --month <YYYY-MM> --part all
   ```

   `all` 依次采集虚拟机、费用、各支柱（可靠性、网络安全、身份安全、性能效率、卓越运营等）和同类对比（peer）。01 的“本月虚拟机使用情况”需要虚拟机清单；卓越运营会复用费用巡检的存储和日志数据，所以建议用 `all`。指标和活动日志看采集当天之前 30 天。输出里的读取失败、无权限要转告用户，不要重试绕过。

   有支柱采集失败时，命令最后会列出失败的支柱和补采命令，并返回非零退出码。有订阅的费用没读到（限流或服务端出错，采集时已自动补读过一轮）时也一样：命令列出这些订阅和 `--part cost --resume` 补读命令，过一段时间后运行。`all` 中途出错或被中断时，会列出还没完成的部分，按提示逐个补采，**不要漏掉 `--part peer`**，否则 05 没有资源创建时间。

   大租户的费用采集可能要十几个小时。中途中断（电脑重启、休眠、网络断开）后，费用部分加 `--resume` 重跑：

   ```bash
   python "<skill>/scripts/azinspect_cli.py" collect --workspace "<工作目录>" --month <YYYY-MM> --part cost --resume
   ```

   `--resume` 只复用同一个月、同样查询、7 天内成功读取的结果，失败或无权限的部分会重新读取；输出最后会写复用了多少、重新读取了多少。资源组超过 100 个的订阅，逐资源费用自动按每批 50 个资源组分段读取，中断后只补读没完成的批次。不加 `--resume` 时照常全部重新读取。虚拟机、WAF 和同类对比的采集不支持续采（WAF 可用 `--pillars` 单独补采）。

2. **分析**（离线，查询官网公开价格）：

   ```bash
   python "<skill>/scripts/azinspect_cli.py" analyze --workspace "<工作目录>" --month <YYYY-MM> --part all
   ```

3. **撰写说明**：按 `references/narrative-format.md` 读数据，写 `narrative/01.json` 至 `narrative/05.json`，最后写 `narrative/00.json`；写法见 `references/writing-style.md`。01 的重点是费用变化原因（`driverNotes`）、要点（`highlights`）和具体建议（`actions`）；03、04 的重点是前十大问题（`topIssues`，含根本原因）、各检查项的主要发现（`checkNotes`）和处理顺序（`actionPlan`）。有外部证据需要调整严重程度时用 `severityOverrides`，必须写理由。不写也能生成，但只有默认文字。

4. **生成并核对**：

   ```bash
   python "<skill>/scripts/azinspect_cli.py" build --workspace "<工作目录>" --month <YYYY-MM> --part all
   ```

   生成 `reports/` 下的 Markdown、Excel 和图表，并自动核对：Excel 公式复算、合计与原始数据一致、读取失败未按 0 处理。核对失败时按提示修改说明文件或补数据，不要改核对脚本。

5. **交叉核对**：

   ```bash
   python "<skill>/scripts/azinspect_cli.py" crosscheck --workspace "<工作目录>" --month <YYYY-MM>
   ```

   逐条处理“需要处理”的规则（明细在 `findings/crosscheck.json`，每条带建议做法），见 `references/cross-checks.md`：降配冲突写进 `narrative/02.json` 的 `crossCheckNotes`（决定暂不调整的加 `"keep": true`，然后重新运行 `analyze --offline` 再 build，这些机器才会从建议和节省里去掉）；不宜降档的数据库或缓存写进 `narrative/01.json` 的 `downsizeExclusions`。改完重新 build 再跑 crosscheck，直到没有“需要处理”。“需人工确认”的逐条看一遍，必要时改说明文件。

6. **质量检查**：

   ```bash
   python "<skill>/scripts/azinspect_cli.py" quality-check --path "<工作目录>/<YYYY-MM>/reports"
   ```

   除格式外，还检查写法，不通过就不能打包：
   - 内部用语和巡检过程用语（如“跨报告”“命中”“未自行”）
   - “需客户确认后执行”每份报告最多 2 次
   - 否定和保留说法（“不等于”“不能据此”等）每万字最多约 6 处
   - 00 的立即处理问题、03/04 的前十大问题，标题或描述里必须点名具体资源或订阅；“影响”每条都写或都不写
   - 选了 01 或 02 时，00 结论要有金额（照抄第 1 节表格里的数字）；没选时不要写费用或金额；结论都要点名最需要处理的资源
   - 连续 3 个以上列表项都只有一个字（说明文件里的文字被逐字拆开）
   - 单个 Markdown 超过 500 KB（明细放 Excel，Markdown 只保留汇总）
   - 报告生成后不能手工修改

   有问题就改 `narrative/*.json`，重新 build 后再检查，直到通过。脚本自动生成的文字触发检查时，告诉用户这是插件问题。

7. **打包**：

   ```bash
   python "<skill>/scripts/azinspect_cli.py" package --workspace "<工作目录>" --month <YYYY-MM>
   ```

   生成 `package/<客户>_Azure巡检报告_<出具月份>/` 和同名压缩包，逐字节核对。交叉核对还有“需要处理”时会拒绝打包；只加了提醒、决定保留建议的，用 `--allow-open`，并在交付时告诉用户。

只重跑部分支柱时用 `--pillars`（逗号分隔），例如某个支柱采集失败后：`collect --part waf --pillars operations,amba`。可选：reliability、aprl、security_network、security_identity、defender、performance、operations、amba、landing_zone。

采集输出里出现“采集失败”时，不要用其他方式绕过；把错误原文告诉用户。被只读白名单拦截（BlockedRequest）说明脚本要发出的请求不在允许范围内，需要修改脚本，而不是放宽规则。

完整流程与进度：

| 阶段 | 做什么 | 命令 | 状态 |
|---|---|---|---|
| 1 采集 | 只读采集费用、资源配置、指标；保存去敏感信息后的原始数据 | `collect` | 01–04 可用 |
| 2 分析 | 按 `references/check-catalog.md` 判断问题，生成问题清单 | `analyze` | 01–04 可用；新增检查项开发中（M3） |
| 3 同类对比 | 对有问题的资源找标准做法和偏差 | `--part peer` | 可用 |
| 4 撰写说明 | **由你根据数据写**，格式见 `references/narrative-format.md` | — | 01–04 可用 |
| 5 生成报告 | 生成 Markdown、Excel、图表并核对 | `build` | 00–05 可用 |
| 6 交叉核对 | 检查报告之间的矛盾 | `crosscheck` | 可用 |
| 7 质量检查 | 星号、图片、表格列数、内部用语、邮箱、保守说法、点名资源、手工修改 | `quality-check`、`package` | 可用 |
| 8 打包 | 中文文件夹和压缩包，逐字节核对 | `package` | 可用 |
| 9 跨月跟踪 | 与上月比：新增、已解决、仍未处理 | build 时自动 | 可用 |

## 跨月跟踪

每次 build 生成 03/04 时，自动把当月问题（稳定编号）存到 `<工作目录>/state/months/<月份>.json`，并与最近一个更早的月份比较，结果写入 `findings/tracking.json`：

- **新增问题**：上月已执行这项检查，本月才出现。
- **新增检查项发现**：本月起新增或首次成功执行的检查发现的问题。不代表情况变差，报告会写明是哪些检查。
- **仍未处理**、**已解决**；对应检查本月有读取失败的（哪怕只是部分失败），或问题所在订阅、所属支柱本月没有检查的，算“本月未检查”，不算已解决。上月不在范围内的订阅本月出现的问题，算“新增检查项发现”。订阅范围变化后，同一问题可能被重新分组（例如原来跨 3 个订阅的一条变成每个订阅一条），按涉及的资源认作同一问题，算“仍未处理”。报告会分别说明“本月未检查”中有几项是读取失败、几项是不在本月范围。

03/04 报告开头会有一句与上月的对比，Excel 问题清单有“与上月相比”列，另有“上月问题处理情况”页；00 汇总的总体结论表多一行。第一次巡检没有对比。撰写 00、03、04 说明时，引用这些数字，不要另行统计。

## 写报告时

- **先读写法规范**：`references/writing-style.md`。要点：
  - 先说建议、费用和预计节省，再简短说明依据和限制。
  - 用直白中文，不写内部过程。
  - 公开价格标注“Azure 官网公开列表价”。
  - 区分问题条数和涉及资源数。
- **每个问题都与同类资源对比**：说明根本原因和对齐标准的做法（`references/peer-comparison.md`）。
- **严重程度按 `references/check-catalog.md`**：有外部证据时可以调整，但要写明理由。
- **只做部分报告时**：`narrative/00.json` 的结论、立即处理的问题和处理计划只写所选报告的内容，不提没做的报告（例如没选 02 就不写降配节省）。脚本生成的部分已经按所选报告处理。

## 交付给用户时

告诉用户以下几项，然后给出交付文件夹和压缩包的路径：

- 各报告的关键数字
- 需要客户确认的事项
- 交叉核对发现的冲突和处理方式：只加了提醒、没改建议的，要说明
- 无法读取的范围
